## 内核隔离是什么？

内核隔离（Kernel Isolation）里的核心功能叫**内存完整性（HVCI，Hypervisor-protected Code Integrity）**，简单说：

> 用虚拟化层把"检查内核代码签名"这件事搬到 Windows 内核管不到的隔离区里做，防止恶意驱动和内核漏洞攻击往内核里塞代码。

听着很美好，但它是有代价的：每次内核调用都要多过一道隔离区里的签名校验，**这个开销在老 CPU 上特别明显**（Intel 11 代之前没有 VBS 硬件加速），实测普遍 5%~15%。而它防的定向 APT 攻击、内核级 rootkit，对个人用户来说风险其实很低——属于"企业防御价值大、个人日常收益小"的功能。

## 排查：怎么确认它开着、谁开的

**第一步：确认它在运行。** 管理员 PowerShell：

```powershell
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard
```

看两个值：

* `VirtualizationBasedSecurityStatus = 2`（VBS 正在运行）
* `SecurityServicesRunning = {2}`（正在运行的服务里包含 HVCI，2 就是内存完整性）

**第二步：查是谁开的。** 这一步很关键，尤其是公司电脑——你不知道是系统默认还是 IT 策略强制。看注册表：

```powershell
# HVCI 场景键
Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity"

# 策略键（GPO/MDM 下发会写在这里）
Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\DeviceGuard"
```

我查到的结果：

* `Enabled=1`、`WasEnabledBy=1`
* 策略键**不存在**

查了微软 Learn 文档确认：`WasEnabledBy=1` 是 **Windows 默认/OEM 镜像启用**的标准配置（管理员手动设置的写法是 2），加上没有策略键，结论：**是 Win11 自己默认开的，不是公司 IT 也不是第三方软件**。Win11 从 22H2 起对 8 代酷睿以后的机型默认开启内存完整性，我的 10 代 i5 正好在自动启用范围内。

> 顺带排除了一个担心：公司装的零信任客户端并没有通过策略强制这个功能，关掉不会踩合规红线（稳妥起见关掉后观察了一天，连接正常）。

## 解决：怎么关

图形界面就能关，30 秒：

1. 开始菜单搜「内核隔离」，打开「内核隔离详细信息」（或 Windows 安全中心 → 设备安全性 → 内核隔离详细信息）
2. **内存完整性** → 关
3. 重启

**重启后验证**（关键，不验证等于白干）：

```powershell
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard | Select-Object SecurityServicesRunning
```

重启前 `{2}`，重启后变成 `{0}`（没有安全服务在跑），说明真的关掉了。

想连 VBS 主开关一起彻底关（裸 VBS 还有 1%~3% 残留开销）：

```powershell
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard" -Name EnableVirtualizationBasedSecurity -Value 0 -Type DWord
```

改注册表前记得先备份：

```powershell
reg export "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard" DeviceGuard-backup.reg
```

回滚就是把 `Enabled` 设回 1，重启即可，无损可逆。

## 第二刀：遥测计划任务的微 IO 风暴

关内核隔离之前一周，我先处理过一次「磁盘永远 100%」。当时的排查走过弯路——用进程吞吐排行找元凶，结果第一名是 dwm（桌面窗口管理器），这明显不对。后来才想明白：

> **换页和微 IO 这类小文件高频读写，看字节速率排行是抓不到的，必须用 `\Process(*)\IO Read Operations/sec`（IO 次数排行）。**

按次数一排，真凶现形：`compattelrunner`（兼容性遥测）每秒几十次小读，而且有一个实例从 9 月 30 号挂到 10 月 8 号都没退——僵尸进程 + 微 IO 风暴。

处理方式是禁用 7 个遥测相关计划任务（CompatTelRunner、PcaPatchDbTask、Appraiser、CEIP Consolidator、UsbCeip、MareBackup、Device Information）。查过风险：唯一实质影响是 Appraiser 被禁后 Windows Update 可能不主动推**功能大版本**（月度安全补丁不受影响），可接受。一行命令看状态：

```powershell
Get-ScheduledTask | Where-Object { $_.TaskName -match 'CompatTelRunner|PcaPatchDbTask|Consolidator|UsbCeip|MareBackup|Appraiser|Device Information' } | Select-Object TaskName, State
```

执行后当场见效：**磁盘活跃 100% → 18.3%，IOPS 300~500 → 218**，第二天重启复查依然有效。

两个坑提前说：

1. **微软会翻回去。** `PcaPatchDbTask` 被禁后，30 分钟内、以及每次重启时，系统都会自动把它重新注册回 Ready——我连续观察了两天都这样。要么定期重跑禁用脚本，要么干脆放任（它触发频率不高）。
2. **升大版本前记得把任务重新启用**（`schtasks /Change /TN <任务名> /ENABLE`），否则更新评估可能不正常。

## 第三刀：关掉 Windows 沙盒，终结开机磁盘 100% 五分钟

遥测清完之后磁盘平时是安静了，但**每次开机头 5 分钟磁盘还是 100%**。这次直奔主题抓开机元凶，发现一个陌生进程：`vmmemCmFirstBoot`。

拆名字就懂了：

* `vmmem` —— 任务管理器里的伪进程，显示的是**虚拟机**占用的内存/磁盘，不是真实程序
* `Cm` —— Container Manager，Windows 容器/沙盒框架
* `FirstBoot` —— 开机跑一次的"首启初始化 VM"，给沙盒准备基础镜像，跑完退出后交给常驻的 `vmmemCmZygote`

为什么我机器上有这套东西？查了一圈服务，是公司的深信服 aTrust 零信任客户端在跑，它依赖 Windows 容器/虚拟化框架做流量沙箱隔离。也就是说这是个"被公司软件拉起来的系统功能"。

关闭方式（管理员 PowerShell 或 DISM）：

```powershell
# 查看当前状态
dism /online /get-featureinfo /featurename:Containers-DisposableClientVM

# 关闭（重启生效）
dism /online /disable-feature /featurename:Containers-DisposableClientVM /NoRestart
```

重启后验证：任务管理器搜 `vmmem` 应该一个都搜不到；再用 CBS 注册表确认功能包状态从「已安装(112)」变成「未激活(64)」：

```powershell
Get-ChildItem "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\Packages" |
  Where-Object { $_.PSChildName -match "DisposableClientVM" } |
  ForEach-Object { "{0} => {1}" -f $_.PSChildName, (Get-ItemProperty $_.PSPath).CurrentState }
```

最关键的验证是 **aTrust 还能不能连公司网络**——实测能，三个 Agent 进程照常工作。这个功能对我就是纯负担，关了不心疼。桌面留了一个重新开启的脚本，哪天要用 Windows 沙盒本身（或 Docker 的 Windows 容器模式）一键开回来。

> 顺带修正一个我自己犯过的错：`vmmemCmZygote` 这个常驻进程，我一开始猜是 MuMu 模拟器的虚拟机，后来又推断成腾讯应用宝的安卓容器——**都不对**。最后是靠实验定案的：把沙盒功能一关，`vmmemCm*` 全家彻底消失。归因这种事，猜十次不如做一次开关实验。
>
> 另一个附带教训：这个进程显示提交量 790 MB，但**工作集是 0**——内存早就被系统换出去了，看着吓人实际几乎不占物理内存。**提交量 ≠ 物理占用**，这条判断标准后面还会用到。

## 第四刀（免费）：重启，比你想象的有用

排查中间有个阶段怎么都找不到元凶，各种指标都"看起来正常"，直到注意到一个前提问题：**这台机器已经连续 8 天没重启了**。

重启前后用同一套只读脚本（内存/池/句柄/进程/驱动快照）做了 A/B 对比，结果相当打脸——我之前一直在分析"哪些驱动占内核池"，实际上：

| 指标 | 重启前 | 重启后 | 变化 |
|---|---|---|---|
| 已用内存 | 12.29 GB | 7.35 GB | **-4.94 GB** |
| 提交量 | 26.7 GB | 7.7 GB | **-71%** |
| **非分页池** | 1297 MB | 494 MB | **-62%** |
| 分页池 | 1772 MB | 385 MB | -78% |
| 句柄总数 | 332015 | 92050 | **-72%** |
| System 进程句柄 | 151479 | 5386 | **-96%** |
| 运行中驱动 | 212 | 211 | 几乎没变 |

最后一行是关键：**驱动数完全没动，内核池却掉了 62%**。说明那 1.3 GB 非分页池的大头根本不是"驱动太多"，而是**8 天累积的内核对象碎片**——长时间不重启，池分配碎片化、对象不回收，重启一次性清零。

所以对老机器来说，**"定期重启"是收益最大的免费操作**，没有之一。我后来把判断标准也改了：不看内存百分比（日常办公负载本来就在 70% 上下，正常），看两个硬指标——**页面文件峰值是否 > 0**（在换页）和**内存压缩区是否 > 400 MB**（有压力）。

## 反面教材：内存优化软件的真实嘴脸

排查期间机器上还装着 **Wise Memory Optimizer**，就是那种点一下"优化"、任务管理器数字立刻变好看的软件。我做了一次很干净的 A/B 实验：同一次开机内、间隔 23 秒、只做一件事（点它的 Optimize），前后各采一次样：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 已用内存 | 11.82 GB | 7.87 GB | **-3.95 GB（假象）** |
| **提交量** | 17231 MB | 17269 MB | **+38 MB（等于没动）** |
| **内存压缩区** | 946 MB | 2433 MB | **+157%** |
| 被压缩最狠的进程 | — | VS Code 工作集 31 MB（真实 299 MB） | — |

看懂了吗：那"释放"的 10.7 GB 工作集，一字节都没还给你，**全被塞进了内存压缩区**。之后每敲一次键盘、切一次标签，系统都得先从压缩区把页面解压回来——**卡顿不是消失了，是改账期了**。补测 5 分钟后工作集自己爬回来，提交量反而比优化前更高。

这类软件的唯一技术手段就是 `EmptyWorkingSet` API，微软文档写明它只是"把页面从工作集移除"。结论：**对内存紧张的机器是负收益**（尤其跑构建、写代码的场景，文件缓存被踢掉直接拖慢编译），建议卸载。判别口诀送给大家：**任何"优化后任务管理器数字变好看"的软件，都值得用提交量复核一遍。**

## 顺手做的：打包前腾内存

这台机器还有个硬需求：前端项目（74 万行）必须本机打包，`--max-old-space-size=8192` 要预留 8 GB。为此写了个打包前的一键脚本，套路是"默认演练、`-Apply` 才执行、有硬保护名单（explorer/Defender/aTrust 等永不杀）、只动有窗口的进程、关闭记录可回滚"。实测两档：

* 普通模式回收 5.1 GB（可用 1.68 → 6.79 GB，不够）
* 加上 Chrome 一起收：**回收 7.04 GB，可用 8.79 GB，刚好够**

顺带发现项目的三个内存放大器：`@vitejs/plugin-legacy`（双份构建）、`terser` 压缩（比 esbuild 慢一个量级）、自定义 `manualChunks` 每个包一个 chunk。这些是另一篇文章的事了。

## 还没打的牌

* **启动项治理**：脚本写好了（三层：自启项 → 服务 → 内核驱动按需加载），目前只跑了演练没执行。Steam、Wallpaper Engine 这类内存大户的自启是最先该关的。
* **32G 单条换装**：这台 E15 只有一个内存槽（WMI `MemoryDevices=1`，双通道物理不可能），官方标最大 16G，但 32G 单条实测有兼容先例，约 ¥600——对症"多开必爆换页"这个真瓶颈。
* **ThrottleStop 解功耗墙**：PL1 15W → 25W + 清灰换硅脂，预估持续性能 +20%，代价是风扇和电池续航。
* **死路提醒**（别被网上教程割韭菜）：这台机器**双通道不可能、XMP 没有、降压被 10 代微码锁死**。

## 针对哪些电脑？适用性自查

这套组合拳**不是对所有机器都有用**，对着下面清单自查：

**适合折腾的：**

* Win11（尤其 22H2 之后的全新安装）且没主动设置过的——内核隔离大概率默认开着
* CPU 较老：Intel 10 代及更早、AMD Zen2 之前——没有 VBS 加速，HVCI 开销最大，收益也最大
* 老机器、内存紧张的机器——HVCI 本身还占几百 MB 内存
* 磁盘长期 100%、开机卡几分钟的——先查遥测任务和沙盒类虚拟机进程
* 连续多天不重启的——先重启再看，别急着卸软件

**不适合照搬的：**

* 新平台机器（Intel 11 代+ / AMD Zen2+）：HVCI 开销已经很小，收益有限
* **公司管控设备**：动系统组件前先查策略键（GPO/MDM 下发的会被拉回来，还可能违规）；遥测任务、沙盒功能动之前也确认下 IT 政策
* 依赖 VBS 的场景：开了「增强登录安全（ESS）」的 Windows Hello、部分企业安全方案——关 VBS 主开关前要确认
* 机器本身没毛病的：如果内存 32G、NVMe 固态、日常占用 40%，上面这些做完了你什么都不会感觉到

**最重要的预期管理**：这套组合拳的实际收益是"消除卡顿病灶 + 白捡 15% 上下"，**不是起死回生**。如果卡顿来自内存容量（多开换页）或硬盘老化，开关救不了，该加内存加内存、该换盘换盘——这台机器物理上限摆在那（15W 四核 U、单通道），能榨的就这么多了，但每一分钱和每一个开关，都该花在刀刃上。
